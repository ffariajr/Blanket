### [001] Editing client's own cell can show a stale value after a same-cell race, with no self-correction

- **Area:** WS collab (Section E — race conditions, rapid-fire same-cell edits from 3+ clients)
- **Severity:** medium
- **Found by:** Section E WS matrix subagent, "race conditions" item — 3+ real Chromium clients (puppeteer-core), same tab_id, rapid-fire edits to the same cell
- **Verified:** yes (by: a separately-dispatched Section E "Mobile ↔ Mobile" subagent — see Verify detail below; originally reproduced twice by the finder, in two separate runs/scenarios, see below)
- **Reproduction:**
  1. Create a throwaway spreadsheet/tab, grant anonymous edit access (or use 3+ distinct authenticated users with edit access).
  2. Open 3+ real browser clients (distinct browser contexts) on the SAME tab_id.
  3. Have all 3+ clients, at nearly the same instant (`Promise.all`, no stagger), select the SAME cell and commit a distinct value each (click cell, Enter to begin edit, type value, Enter to commit).
  4. Wait out the server's debounce window (~7s) for propagation/persistence to settle.
  5. Compare: (a) the value shown in each client's own DOM for that cell, (b) the authoritative persisted value in `spreadsheet_history` (latest `sequence` row) for that tab_id.
  - Confirmed twice: run 1 (5 clients, cell `B1`, tab 1796) — 4 of 5 clients converged on `VALUE_CAROL`, matching the DB's persisted final state, but the 5th client (`Carol`, whose own edit `VALUE_CAROL` is the one that actually won/persisted) displayed `VALUE_ALICE` instead — its own screen never showed the value it had just typed and that in fact became the true final document state. Run 2 (3 clients, plain cell `D1`, no `ACTIONGROUP` involved, isolating the mechanism from that feature): 2 of 3 clients converged on `RACE_THREE` (matching the DB), but the 3rd client (`Race3`, author of the winning `RACE_THREE` edit) displayed `RACE_ONE` — again the stale value of a losing peer, not its own winning edit, and not the true document state.
- **Expected vs. actual:** Expected: after a same-cell race settles, every connected client's own view converges to the same value as the authoritative persisted document (last-write-wins, but consistently so for every viewer, including the "winner"). Actual: the client whose own edit becomes the authoritative value can be left permanently displaying a stale, different value (a losing peer's earlier edit) for that exact cell — diverging from both the DB's persisted state and every other client's (correctly-converged) view. It does not self-correct without a reload/reconnect (which re-fetches the full `state` message) or another edit to that same cell.
- **Root cause (from reading the code, not yet fix-verified):** `ws-server/session.py`'s `_broadcast_others()` only relays an accepted `new_edit` to OTHER clients, never back to the sender (by design, to avoid echo) — so the client whose edit ends up being the server's last-processed (and thus authoritative) value for a cell never receives any message correcting/reconfirming that cell after its own local, optimistic render. Meanwhile `assets/js/grid.js`'s `applyRemote()` (wired from `assets/js/app.js`'s `onRemoteEdit: (patch) => grid.applyRemote(patch)`) unconditionally overwrites `this.cells[ref]` with whatever remote patch arrives, with no version/ordering check against a newer, not-yet-superseded LOCAL edit to that same ref. Because each client also applies its own edit locally and instantly (`setCellValue()`, well before the 400ms `EDIT_DEBOUNCE_MS` client-side send debounce in `ws.js` even fires the network send), there's a window where a peer's older edit can arrive and overwrite the local optimistic render — and because the sender never gets its own edit echoed back, that overwrite is never subsequently corrected once the local edit actually reaches and wins at the server.
- **Verify detail:** Independently reproduced from scratch by a different subagent (dispatched separately for the Section E "Mobile ↔ Mobile" matrix item, not told this entry's conclusion beforehand — this file was read only after already reproducing and root-causing the bug independently). Confirms the bug is broader than "3+ clients, rapid-fire" implies: it reproduces with just **2** clients, **1** simultaneous edit each (no rapid-fire needed), and with **both** clients mobile-emulated (real Chromium, iPhone 13 + Pixel 5 device profiles via `puppeteer-core`, real WS against the actual `blanket-ws` server at `https://church.dogmanjr.net/blanket/`, not local `php -S` — that dev server can't proxy the WS upgrade at all, confirmed separately, so real-WS mobile testing needs the live site or a real Apache+`mod_proxy_wstunnel` path). Isolated repro: two mobile clients (2 distinct throwaway users, both `edit` access) simultaneously typed into the same never-before-touched cell (`E1`) — one `AAAA`, the other `BBBB` — then the test waited 8s (past the 5s server debounce) with NO further interaction. Client A's DOM settled on `BBBB`; client B's DOM settled on `AAAA`; `spreadsheet_history` (latest sequence for the tab) showed the authoritative persisted value was `AAAA`. So client A (whose display showed `BBBB`) was permanently wrong relative to both the DB and client B's own (correct) view, with no self-correction — and a hard reload of client B (which re-fetches full `state`) correctly showed `AAAA`, confirming the DB value was truth and client A was the one left stale. This matches this entry's documented mechanism exactly (the "winning" sender never gets its own edit echoed back, so a peer's earlier, now-superseded broadcast can permanently squat on the winning sender's own cell display). Also separately confirmed via the same setup: presence roster accuracy/distinct colors/clean disconnect-removal, and correct lossless sync for edits to *different* cells, all worked correctly for the Mobile↔Mobile pairing — this same-cell race is the one deviation found in that matrix cell. Given it reproduces from a single simultaneous pair of edits (not requiring 3+ way rapid-fire), and directly undermines confidence in the headline real-time-collab feature with a silent, non-obvious, non-self-healing symptom, recommend Fernando reconsider whether `medium` still fits, or whether this is closer to `high` — leaving the actual severity field as originally logged rather than unilaterally overriding it.

  **Additional independent cross-confirmations** (gathered during a later Section E automated WS collaboration matrix sweep; logged here rather than as separate top-level entries, per this file's "one entry per bug" rule, since each is the same underlying defect reproduced in a further distinct platform pairing/scenario):
  - **Web ↔ Web (3-client and 5-client real-browser reruns):** Reproduced 4 times across 3 scenarios (3 clients twice, 5 clients twice; fresh throwaway spreadsheets/tabs each time, e.g. spreadsheet 687/tab 1786 and, independently, spreadsheet 14444/tab 1879/cell `C7` with users Alpha1/Bravo2/Charlie3). Every time, the client whose own edit was the true authoritative/DB value instead displayed a losing peer's earlier edit. Example: DB/authoritative = `CC-3-Charlie3-matg` (Charlie3's own edit); Alpha1 and Bravo2 correctly converged to it, but Charlie3 itself displayed `BB-2-Bravo2-jbtz`. Repeated immediately after with the same 3 clients/cell: again DB = `CC-3-Charlie3-jek9` (Charlie3's edit won), but Charlie3 displayed `AA-1-Alpha1-9iy6` instead. A related, distinct-looking anomaly was also observed once in a 5-client run against a different cell (`D9`): rather than a stale-peer display, the eventual winning client showed a *blank* cell, and the DB's history table showed the very last of 5 same-second history rows had silently dropped the `D9` key entirely even though earlier rows had it — flagged as a possible second, timing/flush-related bug, not chased further since it was outside the scope of this confirmation.
  - **Web ↔ Mobile (desktop web client vs. mobile-emulated client):** Reproduced via real Chromium, one page desktop-viewport (`isMobile:false`), one page mobile-viewport+touch-emulated (`isMobile:true`), both against the real production WS server, each in its own incognito browser context. Both edited cell `D4` simultaneously (`D-6ql0` from the desktop client, `M-96ij` from the mobile client). An independent third "oracle" WS connection confirmed server truth = `D-6ql0` (the desktop client's own edit) — yet the desktop client's own DOM showed `M-96ij` (the mobile client's losing edit) instead of its own winning value, unresolved 7.5s+ later (well past both the 400ms edit debounce and the 5s save debounce). Root cause confirmed identical (`ws-server/session.py`'s `_broadcast_others()` skip-sender behavior + `assets/js/grid.js`'s unconditional `applyRemote()`), confirming the bug is platform-agnostic (same client code path on web and mobile), not a Web/Mobile message-format mismatch. A related, more severe variant was also observed when edits used realistic character-by-character typing instead of an atomic value-set: a remote patch arriving mid-keystroke destroyed the in-progress `<input class="cell-input">` outright via `_renderCell()`'s `innerHTML=''`, silently discarding that client's edit before it was ever sent — this is the same destructive-remote-patch-during-open-edit mechanism documented as its own, more severe, finding (see `[016]` below).
  - **Mixed 2-web + 2-mobile (4-way simultaneous):** Reproduced with 2 web-viewport and 2 mobile-viewport/touch-emulated real Chromium clients (4 distinct throwaway users) all committing distinct, complete (non-interrupted) edits to the same cell (`B1`) within the debounce window. 3 of 4 clients converged correctly on the true DB-authoritative value (`race-mob1`), but the 4th client — the actual author of that very value — displayed a different, already-superseded peer value (`race-mob2`) instead of its own winning edit, with no self-correction. Confirms the defect reproduces identically across web/mobile mixes and with more than 2 simultaneous editors.
  - **Section E rapid-fire re-run (5 fully-anonymous real Chromium clients, fresh spreadsheet/tab, cell `C7`):** 4 of 5 clients converged on the true DB-persisted value (`V_Charlie_vzwl`); the 5th client (`Charlie`, whose own edit is what actually won and persisted) displayed a different, stale peer value (`V_Alpha_pl4y`) instead. Reproduced on the very first attempt with no retries needed, further confirming this is a reliable, easily-reproducible defect rather than a rare timing fluke.

  Taken together with the original finding and its earlier Mobile↔Mobile confirmation, this defect has now been independently reproduced across every platform pairing tested (Web↔Web, Web↔Mobile, Mobile↔Mobile, and 4-way mixed), each time from freshly-created throwaway data with its own random suffix (cleaned up by exact ID afterward, spreadsheet id=13 never touched) — recommend Fernando treat this as a confirmed, highly-reproducible, cross-platform defect in the core real-time-collaboration feature, not an edge case specific to any one client type or scenario.
- **Status:** fixed (commit `6cb0b48`)

### [002] Cell and row/column-header context menus have no mobile touch equivalent — Insert/Delete row/column completely unreachable via touch; Cut/Paste/Clear-contents unreachable outside a physical keyboard

- **Area:** Mobile touch / feature parity (Section B Part 2 — context menus)
- **Severity:** high
- **Found by:** Section B Part 2 feature-parity subagent, "context menus" item
- **Verified:** no — see detail (not yet independently re-verified by a second agent; logging now per the rule that an unconfirmed finding still gets recorded rather than discarded)
- **Reproduction:**
  1. `grid.js`'s only listener that opens a context menu is `this.container.addEventListener('contextmenu', ...)` (`_onContextMenu`, grid.js ~line 166/996), which dispatches a `gridcontextmenu` CustomEvent that `app.js` (~line 830) turns into the actual `.tab-menu` popup via `showCellContextMenu`/`showHeaderContextMenu`. There is no other code path anywhere in `assets/js/*.js` that ever opens this menu, and no `long-press`/`longpress` handling exists in the codebase at all (confirmed via `grep -ri "long.press" assets/js/*.js` — zero matches).
  2. The grid's own touch handling (`_onTouchStart`/`_armTouchDragCandidate`/`_onTouchMove`/`_onTouchEnd`, grid.js ~lines 1134-1232) is the only thing that reacts to a finger held still on a cell/row-header/col-header: after `TOUCH_DRAG_ARM_MS` (350ms) of no movement it "arms" and starts a **drag-select** (`this._select()`/`selectWholeRow()`/`selectWholeColumn()`), not a context menu. It never dispatches `contextmenu` or `gridcontextmenu`.
  3. Reproduced empirically with a real Chromium instance (`puppeteer-core`, mobile emulation: 390×844 viewport, `isMobile:true`, `hasTouch:true`, iOS Safari UA) against a throwaway spreadsheet/tab: dispatched a genuine touch sequence on a cell — real `touchstart`, held 700ms (past the 350ms arm timer, no movement), then real `touchend` — with `gridcontextmenu`/`contextmenu` listeners armed beforehand. Result: **zero** `contextmenu`/`gridcontextmenu` events fired, and no menu ever appeared; the only observable effect was the cell becoming selected (the drag-select-arm path claiming the gesture), confirmed via a screenshot showing the formula bar's reference label updating to `A1` with the cell highlighted, no menu present.
  4. As a control, manually dispatching a synthetic native `contextmenu` `MouseEvent` at the same cell (simulating what a right-click, or a browser that DID synthesize one from touch, would produce) correctly opened the real menu (`Copy`/`Cut`/`Paste`/`Clear contents`/`Show browser menu` for a cell; `Insert N row(s) above/below`+`Delete row(s)` for a row header; `Insert N column(s) left/right`+`Delete column(s)` for a column header) with reasonably touch-sized tap targets — so the menu UI itself is fine, the problem is purely that nothing on a touchscreen ever triggers it.
  5. Checked for any alternative UI path to the same actions: `grep`'d `assets/js/app.js` for every call site of `insertRowsAt`/`deleteRowsAt`/`insertColumnsAt`/`deleteColumnsAt`/`_cutSelectionToClipboard`/`_pasteClipboardAtSelection`/`_clearSelection` — the ONLY call sites for all of them are inside `showCellContextMenu`/`showHeaderContextMenu` themselves. No toolbar button, no "+" row/column affordance, nothing in `index.html`, offers any of these anywhere else. The one keyboard-shortcut fallback that exists (`grid.js`'s `_onKeyDown`: Ctrl/Cmd+C, Ctrl/Cmd+V, and Delete/Backspace-clears-selection-when-not-editing) requires a physical keyboard and is irrelevant to a touch-only device with no attached keyboard — Delete/Backspace-while-selected-but-not-editing in particular has no virtual-keyboard equivalent at all, since the on-screen keyboard on mobile only appears once a cell is already in edit mode (double-tap → `_beginEdit`), by which point `_onKeyDown`'s early `if (this.editingInput ...) return;` means that whole branch (and thus `_clearSelection()`) is unreachable anyway.
- **Expected vs. actual:** Expected: per the testing plan's own framing, mobile touch users should either have a working equivalent (e.g. long-press-to-open-menu, matching Google Sheets/Excel mobile — which the code's own comments elsewhere explicitly reference as the intended UX model for touch gestures) or, failing that, some other UI path to the same actions. Actual: there is no long-press-to-context-menu implementation at all, and it was empirically confirmed that a real touch long-press does not open the menu (the app's own 350ms hold-to-drag-select timer claims the gesture first, before any native browser long-press-to-contextmenu synthesis could plausibly fire — and real iOS Safari, the app's actual explicit mobile target per Section B, does not reliably synthesize `contextmenu` from touch on ordinary elements at all, a long-documented WebKit limitation). The consequence: **Insert row above/below, Insert column left/right, and Delete row/column are completely unreachable by a touch-only mobile user** — there is no alternative anywhere in the app. **Cut, Paste, and "Clear contents" (for anything beyond a single cell already in edit mode) are also unreachable via touch alone** — the only alternative (Ctrl+C/V/Delete/Backspace) requires a physical keyboard. A mobile user CAN approximate clearing a single cell by double-tapping into edit mode and manually blanking the field via the virtual keyboard, but cannot clear a multi-cell range in one action, and has no way at all to insert or delete a row/column.
- **Verify detail:** Not yet independently re-verified by a second agent — logged per the rule that an unconfirmed finding is still recorded (not discarded) with `Verified: no`.
- **Status:** fixed (commit `2becf39`)

### [003] Edit committed right before (not after) a WS disconnect is silently and permanently lost — REST autosave fallback doesn't catch it

- **Area:** Section F (a) — WS-drop-mid-edit / REST autosave fallback
- **Severity:** high
- **Found by:** Section F automated extra-scope sweep
- **Verified:** yes (by: an independent second agent — CONFIRMED)
- **Reproduction:**
  1. Set up: throwaway user `wftest_<suffix>` (created via `bin/create-admin.php`), throwaway spreadsheet + tab, logged in against `https://church.dogmanjr.net/blanket/` (real WS server) via `puppeteer-core` + real headless Chromium (per Ground Rules workaround).
  2. Instrument the page (`evaluateOnNewDocument`) to wrap `window.WebSocket` so the app's real WS instance can be captured and later closed programmatically, simulating a genuine mid-session network drop.
  3. Load the tab; confirm status shows "Live" (WS connected).
  4. Use a real Puppeteer click (`page.click`, not `element.click()`) to select a cell, type a distinct value, press Enter to commit (this fires `grid.onChange` → `socket.queueEdit(patch)` [starts 400ms debounce] and `localSaveFallbackTimer()` [no-ops because `isConnected()` is still true at this instant]).
  5. ~60ms later (well inside the 400ms debounce window), call the captured WebSocket instance's `.close()` to sever the connection.
  6. Wait several seconds with NO further edit made. Status dot correctly flips to "Offline", but the "Saved X ago" label never updates and no `/api/tabs/{id}/save` request is ever issued (confirmed via a `fetch()` wrapper logging every request the page made).
  7. Query `spreadsheet_history` directly for that `tab_id`: only the original tab-creation row exists; no new row was ever written containing the typed value — the edit is genuinely and permanently lost (a page reload would show the pre-edit state).
  8. Control test: if a SECOND edit is made after the drop (while status already shows "Offline"), that second `onChange` call correctly sees `isConnected()===false`, schedules the REST fallback, and the resulting save persists BOTH the first (previously stranded) and second edit's values together, since the fallback POSTs the whole in-memory `grid.cells`, not just a delta. This confirms the loss is specific to the no-further-edit case, and that `grid.cells` itself isn't corrupted — only the persistence step for that first edit is dropped.
- **Expected vs. actual:** Expected: per the documented `localSaveFallbackTimer` design (`assets/js/app.js` comments), any edit that isn't successfully carried by the live WS session should fall back to the REST autosave path so no edit is ever silently lost, regardless of exactly when in the WS debounce window the connection happens to drop. Actual: an edit committed right before (but not after) a WS disconnect is neither sent over WS nor picked up by the REST fallback, and is never persisted to `spreadsheet_history` at all unless the user happens to make another edit afterward. Nothing in the UI indicates this specific edit was lost — the cell shows the typed value locally and the connection status only says "Offline", which reads as "not currently live", not "you just lost data".
- **Verify detail:** FULLY REPRODUCED — the reported bug is real, confirmed both by code inspection and by live end-to-end reproduction against the real production WS server (`https://church.dogmanjr.net/blanket/`), independently from scratch.

  Code-level confirmation (root cause matches the report exactly): `assets/js/ws.js` `_flushEdit()` (called only after the 400ms `EDIT_DEBOUNCE_MS` debounce fires) gates solely on `!this.isConnected()` evaluated AT FLUSH TIME, and if disconnected it just `return`s — `_pendingPatch` is never cleared, never retried, and no signal is emitted back to the app. `assets/js/app.js` `localSaveFallbackTimer()` gates on `if (socket.isConnected()) return;` evaluated synchronously at the moment `onChange` fires (i.e. at edit time, ~0ms after commit) — before the WS debounce has had any chance to fail. The `onStatus` handler's `'disconnected'` branch (app.js) only updates the status-dot UI; it never calls `localSaveFallbackTimer()` or otherwise re-checks/requeues any edit that was mid-flight in the WS debounce window. There is no requeue/retry path anywhere in either file.

  Live reproduction (throwaway data only, per Ground Rules — user `wftest_6403d12d` id=209, spreadsheet id=5724, tab id=1844, created via `bin/create-admin.php` + REST API; all deleted by exact ID afterward, verified 0 rows remaining): used `puppeteer-core` + real headless Chromium (per the documented `LD_LIBRARY_PATH` workaround) with `evaluateOnNewDocument` wrapping `window.WebSocket` in a Proxy to capture the app's real socket instance. Pre-seeded `blanket_token` localStorage + `blanket_name` cookie to skip login/welcome-modal, navigated to `#/sheets/5724/tabs/1844`, confirmed status showed "Live". Real `page.mouse.click` on cell A1, typed `WSDROP_<ts>`, pressed Enter (fires `grid.onChange` → `queueEdit` + `localSaveFallbackTimer()`, the latter no-oping since `isConnected()` was still true). 62ms later (well inside the 400ms window) called `.close()` on the captured WS instance. Status flipped to "Offline" ~71ms after commit. Waited 6s with no further edit: a full network-request log showed exactly zero save-related requests (no `POST /api/tabs/1844/save`, only earlier GETs). Queried `spreadsheet_history` directly for `tab_id=1844`: only the original tab-creation row (`cells: {}`) existed — the typed A1 value was never persisted anywhere, confirmed permanently lost. The cell's DOM still showed the typed value locally, matching the report's point that nothing in the UI signals this specific loss beyond the ambiguous "Offline" status.

  Control test (separate run, edits to B1 then C1 to avoid conflating with the first run): first edit dropped via WS close at +63ms, status confirmed Offline at +71ms; then a second edit was made while already offline. That second `onChange` correctly saw `isConnected()===false`, scheduled the REST fallback, and after ~1.2s+ debounce a single `POST /api/tabs/1844/save` fired containing BOTH values in one payload: `{"cells":{"B1":{"value":"FIRST_..."},"C1":{"value":"SECOND_..."}}}`. Verified in `spreadsheet_history` (row id 13465) — both edits landed together in one history row, confirming `grid.cells` itself isn't corrupted; only the persistence step for the stranded first edit was dropped, and it only survives by "hitching a ride" on a later edit's full-state save.

  This exactly matches every claim in the original report, including severity reasoning: an edit made right before (not after) a WS drop is silently and permanently lost unless the user happens to edit again afterward, with no requeue/retry mechanism connecting the WS debounce failure back to the REST fallback path.

  Relevant files: `/home/claude/blanket/assets/js/ws.js` (lines 9, 126-130, 181-186), `/home/claude/blanket/assets/js/app.js` (lines 507-510, 722-739, 763-778).
- **Status:** fixed (commit `6cb0b48`)
